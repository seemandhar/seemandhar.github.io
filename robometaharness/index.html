Abstract

Frozen robot policies often fail when instructions, scene layouts, or execution conditions change, even though they have the motor skills the task needs. A harness, the program around a frozen policy, can repair such failures at inference time without updating weights. But harnesses are built by hand around one policy interface and are hard to combine, and automated harness optimizers search only within the interfaces they start with. We argue that harness discovery is two problems: growing what a harness can express, and finding the harness a deployment needs.

RoboMetaHarness addresses them with two coupled loops, each run by a multi-agent pipeline. Loop 1 is HarnessStudio, a self-improving research substrate with interfaces to more than 20 benchmarks and 20 policies. It ports published inference-time methods into one shared runtime, adds the policy and sensor interfaces they require, and keeps the code and lessons of every experiment, so that separate methods become interoperable and new kinds of intervention become available to all later searches. Loop 2 diagnoses the failures of a given frozen policy, composes existing and new mechanisms into a harness, and accepts it only after paired comparison on fresh episodes.

Across four frozen policies and Diffusion Policy on five benchmarks, including LIBERO-Pro and RoboCasa, discovered harnesses improve on the published harnesses they start from by 5 to 20 points. On two hard LIBERO-Pro settings they more than double the plain policy's success and outperform the harnesses found by existing optimizers and coding agents. Accumulated knowledge turns a failed search into a successful one, and harnesses discovered with one policy transfer unchanged to others. All source code and data will be publicly released.

How it works

Grow the space. Then search it.

Existing harness optimizers fix the space of harnesses and search only inside it. RoboMetaHarness grows the space in Loop 1 and searches it for each deployment in Loop 2.

LOOP 1 / HARNESSSTUDIO

Expand what a harness can express

Research agents read a published method, port it, and review the port. Each method becomes an executable package in one shared runtime that states which interfaces it needs: RGB-D input, token logits, a denoising sampler. When a mechanism needs a missing interface, Loop 1 adds it, after checking that the plain policy's native actions stay identical. Porting PCD added token logits; TTF added a vision-token hook; Harness VLA contributed depth back-projection and geometric motion. Accepted lessons and scoped counterexamples are kept alongside the code.

LOOP 2 / DISCOVERY

Find the harness a deployment needs

Given a frozen policy, a task, and a budget, specialist agents carry out the search: scientists propose, a critic reviews, a coder implements, and a single evaluator runs every experiment, so no agent grades its own work. They diagnose failures in development rollouts, retrieve compatible packages, code, and lessons, and reuse, combine, or extend them. A harness is selected on development episodes, confirmed once on a fresh validation block, and scored on final episodes no search has seen. Its code and lessons then return to Loop 1.

Paired evaluation. Every candidate is compared with a fresh run of its reference, the plain policy or an existing harness, on identical initial states. For N matched cases, W counts reference failures converted to successes and R the reverse; the paired improvement is (W−R)/N, reported with exact McNemar p. Policy and auxiliary-model weights stay frozen, and the benchmark's scenes, horizon, and success check are unchanged.

A common thread: the reference harness aims at the wrong thing

A look-alike object, an empty spot, a wrong drag direction, or a gripper angle successful episodes never used. Each added mechanism corrects that aim and leaves the rest of the harness unchanged. In the development episodes CENSUS rescued, the reference planner staged its first grasp 17 to 36 cm from the instructed object; with the note it staged within 1 cm.

No baseline is strong on both settings

Meta-Harness finds the best baseline harness on task perturbations but one of the weakest on position swap; RoboArchitect is the reverse. Three of six baselines find no harness that passes validation, and random search over the same HarnessStudio library finds none, so access to the library alone does not explain the result. On position swap, RoboMetaHarness's harness is a grounded planner that locates the instructed object with the depth stream Loop 1 added and moves to it with analytic motion tools; it loses most of its successes when either is disabled. The result holds on a second block of 400 new scenes (63.5% vs. 54.5% for RoboArchitect), using about two-thirds of RoboArchitect's development episodes and half its GPU-hours.

Safe to deploy alongside the plain policy

With a check that routes only the tasks a harness was discovered for, the position-swap harness never triggers on 800 object and language perturbation episodes where plain π0.5 already succeeds over 90% of the time, and no success is lost. On the 400 swap episodes it triggers in 390 and success rises from 28.8% to 61.3%. The same harness used unchanged with π0-FAST raises it from 9.5% to 47.5%. At deployment, U5+Z adds no detectable latency: 69 ms median per executed step, the same as the plain policy.
